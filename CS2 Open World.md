# ЧАСТЬ I. КОНЦЕПЦИЯ ПРОЕКТА

## 1. Назначение

CS2 Open World — многопользовательский серверный проект на Counter-Strike 2, создающий платформу открытого мира с ролевыми игровыми системами.

Проект должен поддерживать:

1. Большой игровой мир, разделённый на отдельные секторы.
2. Несколько серверов CS2, совместно обслуживающих этот мир.
3. Переходы игроков между секторами.
4. Сохранение состояния игроков.
5. Собственный интерфейс.
6. NPC и диалоги.
7. Задания.
8. Транспорт.
9. Экономику.
10. Инвентарь.
11. Взаимодействие игроков.
12. Возможность создавать разные игровые режимы.
13. Подключаемые игровые модули.
14. Размещение нескольких серверов на одной машине.
15. Возможность горизонтального масштабирования на несколько машин.

Проект изначально ориентирован на мультиплеер.

Однопользовательский режим не является обязательным, но архитектура не должна препятствовать запуску мира с одним игроком.

## 2. Главные принципы

### 2.1. Модульность

Каждая подсистема имеет чёткую ответственность.

Например:

- Inventory отвечает за предметы.
- Economy отвечает за денежные операции.
- NPC отвечает за NPC.
- Dialog отвечает за разговоры.
- UI отвечает за отображение интерфейсов.

Модули не должны напрямую вмешиваться во внутреннее состояние друг друга.

### 2.2. Расширяемость

Разработчик должен иметь возможность:

- подключить новый модуль;
- отключить необязательный модуль;
- заменить реализацию модуля;
- добавить новый игровой режим;
- добавить новый интерфейс;
- расширить систему NPC;
- создать собственные задания.

### 2.3. Авторитетность сервера

Сервер определяет игровое состояние.

Клиент может отправлять действия и получать результаты, но не должен самостоятельно назначать себе деньги, предметы, здоровье или завершённые задания.

### 2.4. Независимость от способа отображения

Игровая логика не должна зависеть от конкретной технологии интерфейса.

Например, Dialog System не должна знать, используется ли:

- particle-меню;
- Panorama;
- встроенное меню;
- другой механизм отображения.

### 2.5. Независимость от базы данных

Игровые модули не должны напрямую выполнять SQL-запросы.

Доступ к данным осуществляется через Persistence и специализированные репозитории.

### 2.6. Безопасность времени жизни объектов

Указатели на сущности движка не должны храниться без учёта их жизненного цикла.

В долгоживущем состоянии предпочтительно хранить стабильные идентификаторы и проверяемые дескрипторы, а не необработанные указатели.

## 4. Физическое размещение

Один компьютер может запускать несколько игровых серверов.

```text
                 ОДИН ФИЗИЧЕСКИЙ КОМПЬЮТЕР
┌──────────────────────────────────────────────────────────┐
│                                                          │
│  CS2 Server A                  CS2 Server B               │
│  Port A                        Port B                     │
│  Sector: Downtown              Sector: Industrial        │
│       │                              │                    │
│       └──────────────┬───────────────┘                    │
│                      │                                    │
│  CS2 Server C        │                                    │
│  Sector: Airport     │                                    │
│       │              │                                    │
│       └──────────────┤                                    │
│                      │                                    │
│                Coordinator                               │
│                      │                                    │
│                PostgreSQL                                │
│                      │                                    │
│                 Monitoring                               │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

Каждый сервер CS2 является отдельным процессом.

У каждого процесса собственные:

- память;
- игровой мир;
- сущности;
- игровые соединения;
- экземпляр OW Core;
- экземпляры игровых модулей.

Общими являются только данные и сервисы, доступ к которым организован явно.

### Ограничения

Несколько процессов на одной машине не означают общего использования одной копии игровых ресурсов в памяти.

Операционная система может совместно использовать некоторые страницы памяти, но значительная часть состояния каждого сервера остаётся отдельной.

Количество одновременно работающих серверов необходимо определять нагрузочным тестированием.

# ЧАСТЬ III. OW CORE

## 5. Назначение ядра

OW Core — центральный компонент серверного плагина.

Он должен:

1. Инициализировать модификацию.
2. Подключаться к возможностям движка через адаптеры.
3. Управлять жизненным циклом модулей.
4. Предоставлять общие интерфейсы.
5. Организовывать обмен событиями.
6. Управлять игровыми сессиями.
7. Обеспечивать доступ к общим сервисам.
8. Управлять конфигурацией.
9. Контролировать завершение работы.
10. Предоставлять диагностику.

Ядро не должно самостоятельно реализовывать всю игровую логику.

## 6. Module Manager

### Назначение

Управление подключаемыми модулями.

### Основные операции

**DiscoverModules**

Находит доступные модули в разрешённых каталогах.

**ReadModuleManifest**

Читает описание модуля:

- идентификатор;
- версию;
- версию API ядра;
- зависимости;
- обязательные сервисы;
- настройки;
- поддерживаемые платформы.

**ResolveDependencies**

Строит граф зависимостей.

Обнаруживает:

- отсутствующие зависимости;
- несовместимые версии;
- циклические зависимости.

**LoadModule**

Загружает модуль и проверяет совместимость.

**InitializeModule**

Передаёт модулю доступ к разрешённым сервисам.

**StartModule**

Переводит модуль в рабочее состояние.

**StopModule**

Запрещает новые операции и начинает остановку.

**UnloadModule**

Освобождает ресурсы модуля после безопасного завершения.

**GetModuleStatus**

Возвращает текущее состояние модуля.

### Состояния

```text
DISCOVERED
    │
    ▼
VALIDATED
    │
    ▼
LOADED
    │
    ▼
INITIALIZED
    │
    ▼
RUNNING
    │
    ▼
STOPPING
    │
    ▼
STOPPED
    │
    ▼
UNLOADED
```

При ошибке модуль переходит в состояние FAILED.

### Правила

Обязательные модули нельзя отключать, если это нарушит работоспособность ядра.

Необязательные модули могут отсутствовать.

Выгрузка модуля во время игры допускается только при наличии подтверждённого безопасного механизма.

В первой версии допускается отключение модулей через конфигурацию с последующим перезапуском сервера.

## 7. Service Registry

### Назначение

Предоставление интерфейсов между модулями.

Пример:

```text
Inventory Module
       │
       │ Регистрирует IInventoryService
       ▼
Service Registry
       ▲
       │ Запрашивает IInventoryService
       │
Quest Module
```

Quest Module не должен знать, где находится реализация Inventory.

### Основные операции

- RegisterService
- UnregisterService
- GetService
- HasService
- ValidateServiceVersion

### Правила

Интерфейсы должны иметь версии.

Модуль не должен использовать сервис после его остановки.

При выгрузке поставщика сервиса зависимые модули должны быть остановлены либо переведены в предусмотренный безопасный режим.

## 8. Event Bus

### Назначение

Локальная передача событий между модулями одного процесса.

### Примеры событий

```text
Player.Connected
Player.Disconnected

Player.Damaged
Player.Died

NPC.Spawned
NPC.Interacted

Inventory.ItemAdded
Inventory.ItemRemoved

Quest.Started
Quest.Completed

Vehicle.Entered
Vehicle.Exited

Transfer.Started
Transfer.Completed
Transfer.Failed
```

### Основные операции

- Subscribe
- Unsubscribe
- Publish
- RegisterEventType
- DispatchPendingEvents

### Важное различие

**Событие** сообщает о произошедшем факте.

**Команда** запрашивает выполнение действия.

**Запрос** получает информацию или результат.

Например:

```text
Command:
Inventory.AddItem

Event:
Inventory.ItemAdded

Query:
Inventory.GetItems
```

Не следует превращать все взаимодействия в события.

### Правила

Event Bus внутри сервера не равен межсерверной системе сообщений.

События должны иметь определённый порядок обработки там, где он необходим.

Необходимо ограничить рекурсивную публикацию событий и бесконечные циклы между подписчиками.

## 9. Engine Adapter

### Назначение

Изолировать остальную систему от конкретных интерфейсов CS2.

```text
             Gameplay Modules
                    │
                    ▼
               OW Engine API
                    │
                    ▼
               Engine Adapter
                    │
          ┌─────────┴─────────┐
          │                   │
     Metamod Hooks       hl2sdk-cs2
          │                   │
          └─────────┬─────────┘
                    │
                 CS2 Engine
```

### Основные операции

- FindPlayerEntity
- ResolveEntityHandle
- GetEntityPosition
- SetEntityPosition
- SpawnSupportedEntity
- RemoveEntity
- RegisterGameEvent
- RegisterHook
- UnregisterHook
- ScheduleGameThreadTask

Это проектируемые абстракции, а не подтверждённые названия функций SDK.

### Правила

Модули не должны самостоятельно хранить адреса внутренних функций движка.

Работа с хуками централизуется через Engine Adapter или специализированные адаптеры.

Все операции должны учитывать требования игрового потока.

Изменения движка после обновлений CS2 должны по возможности затрагивать адаптеры, а не всю систему.

# ЧАСТЬ IV. ИГРОКИ И СЕССИИ

## 10. Player Manager

### Назначение

Управление подключениями игроков.

### Основные операции

**OnPlayerConnecting**

Начинает обработку подключения.

**AuthenticatePlayer**

Связывает подключение с подтверждённой идентичностью игрока.

**CreateSession**

Создаёт игровую сессию.

**RestorePlayerState**

Восстанавливает сохранённое состояние.

**GetPlayerSession**

Получает текущую сессию.

**OnPlayerDisconnected**

Обрабатывает отключение.

**CloseSession**

Завершает сессию и освобождает связанные ресурсы.

### Данные сессии

```text
PlayerSession
├── PlayerId
├── SessionId
├── ServerId
├── ConnectionState
├── CharacterId
├── CurrentSector
├── CurrentPosition
├── ActiveTransferId
└── SessionGeneration
```

PlayerId и SessionId — разные сущности.

PlayerId идентифицирует игрока.

SessionId идентифицирует конкретную игровую сессию.

### Важное правило

У одного игрока не должно быть двух одновременно авторитетных игровых сессий.

При повторном подключении устаревшая сессия должна быть корректно обработана.

## 11. Character System

### Назначение

Управление игровыми персонажами.

Один аккаунт потенциально может иметь несколько персонажей.

### Основные операции

- CreateCharacter
- DeleteCharacter
- SelectCharacter
- LoadCharacter
- SaveCharacter
- UpdateCharacterProfile
- GetCharacterState

### Состояние персонажа

- идентификатор;
- имя;
- внешний вид;
- здоровье;
- характеристики;
- позиция;
- деньги;
- инвентарь;
- репутация;
- задания;
- принадлежность к организациям.

### Разделение

Player Manager управляет подключением.

Character System управляет персонажем.

Базовый выбор персонажа при входе реализован через асинхронную загрузку списка: единственный персонаж выбирается автоматически, несколько доступны через текстовые команды. Полная Character System — сохранение игрового состояния, профили и spawn/load lifecycle — остаётся отдельной незавершённой задачей.

# ЧАСТЬ V. МИР И СЕКТОРЫ

## 12. World Manager

### Назначение

Представление единого игрового мира, разделённого на секторы.

### Основные операции

- RegisterWorld
- RegisterSector
- FindSectorByPosition
- GetSectorBounds
- GetAdjacentSectors
- ConvertGlobalToLocal
- ConvertLocalToGlobal
- GetSectorServer
- IsSectorAvailable

### Модель мира

```text
                 GLOBAL WORLD

       X →
   ┌──────────┬──────────┬──────────┐
   │          │          │          │
   │ Sector A │ Sector B │ Sector C │
   │          │          │          │
   ├──────────┼──────────┼──────────┤
   │          │          │          │
 Y │ Sector D │ Sector E │ Sector F │
 ↓ │          │          │          │
   └──────────┴──────────┴──────────┘
```

### Системы координат

Каждый объект может иметь:

**GlobalPosition**

Позицию в логическом мире проекта.

**LocalPosition**

Позицию на конкретной карте CS2.

**SectorId**

Идентификатор сектора.

Преобразование:

```text
GlobalPosition
       │
       ▼
Sector Transform
       │
       ▼
LocalPosition
```

Преобразование должно учитывать:

- смещение;
- ориентацию;
- масштаб, если используется;
- высоту;
- допустимую область появления.

### Простой переход между серверами

Для ручного перехода игрок пишет в чат `!go <server_id>` (синоним `!transfer`). OW Core принимает запрос только от полностью Steam-аутентифицированного игрока, находит destination в локальном списке `[servers.*]` и отправляет клиенту `connect` на заранее проверенный endpoint. Клиент не может передать произвольный адрес.

Это reconnect, а не бесшовный переход: автоматического запуска по координатам/trigger, резервирования destination, сохранения полной позиции/состояния и восстановления snapshot пока нет. До реализации этих частей карта может содержать заметные вручную созданные порталы/указатели с названием целевого сервера и подсказкой `!go <server_id>`.

### Бюджет runtime-сущностей карты

Лимит entity system нельзя расширить плагином. SDK задаёт таблицу на 512 entity identities × 64 списка (`MAX_TOTAL_ENTITIES = 32768`), однако это ёмкость пространства индексов, а не допустимый бюджет карты: игрокам и runtime-системам требуется запас. Для больших сцен статический декор следует запекать в world geometry: использовать Hammer `prop_static` и `Force Bake To World` (`baketoworld`), где это подходит, не отключать mesh merging без необходимости, а отдельными runtime entities оставлять лишь реально интерактивные, подвижные, физические или анимируемые объекты. Если динамический контент всё равно превышает доступный бюджет, уменьшайте его или распределяйте по картам-сегментам. Ручное вмешательство плагина в allocator/индексы не является безопасным обходом лимита.

### Границы секторов

Сектор должен описывать:

- идентификатор;
- геометрические границы;
- соседние секторы;
- карту CS2;
- сервер назначения;
- допустимые точки перехода;
- безопасные точки появления.

# ЧАСТЬ VI. МЕЖСЕРВЕРНЫЕ ПЕРЕХОДЫ

### Назначение

### Последовательность

Подготовка данных разделяется на два этапа. До появления игрока на целевом сервере должны быть доступны актуальный transfer snapshot и прочие данные, без которых нельзя безопасно восстановить авторитетное игровое состояние. После их готовности игрок может начать игру; настройки интерфейса, косметика и другие некритичные разделы загружаются фоново и применяются по мере готовности. Ни один фоновый загрузчик не должен обращаться к API игрового движка из рабочего потока.

Данные, влияющие на права доступа, владение сессией, экономику или целостность персонажа, нельзя откладывать до появления игрока, если без них невозможно безопасно разрешить соответствующее действие. Сервер обязан проверять такие операции по авторитетному хранилищу/координатору, а не доверять одному лишь кэшу.

### Важнейшее правило

Одновременно только один сервер имеет право изменять авторитетное состояние персонажа.

Для этого предусматривается механизм владения сессией с поколением или fencing token.

Сервер со старым поколением не должен иметь возможности записать устаревшее состояние поверх нового.

### Обработка сбоев

**Сервер B недоступен**

Переход не начинается.

**Игрок отключился во время перехода**

Операция остаётся в восстанавливаемом состоянии.

**Игрок подключился к B, но подтверждение потерялось**

Повторное подтверждение не должно создавать вторую сессию.

**Сервер A упал**

Coordinator определяет владельца сессии по сохранённому состоянию.

**Истёк срок перехода**

Операция переводится в восстановление или отмену по установленным правилам.

### Ограничение

Полностью бесшовный переход без клиентской загрузки не считается подтверждённой возможностью.

Первая версия должна использовать реально поддерживаемый механизм перехода между серверами.

Предварительный кандидат для проверки — отправка подключённому клиенту команды `connect <адрес>` через серверный интерфейс клиентских команд CS2. Перед отправкой сервер резервирует слот назначения, сохраняет снимок персонажа и выдаёт одноразовый короткоживущий transfer token. Сервер назначения проверяет token и Steam-аутентификацию, затем подтверждает прибытие координатору. Это переподключение, а не бесшовная миграция: загрузка карты и повторная авторизация остаются под контролем клиента и игры. Механизм должен быть проверен на выделенном сервере, включая ограничения client command, таймауты и отказ назначения; открытый ADR-025 остаётся открытым до такого прототипа.

## 16. Cache Manager (локальный кеш настроек и экспериментальный fallback)

### Назначение

Локально ускорять повторное чтение редко меняющихся настроек игрока. Кеш ограничен временем жизни и памятью; PostgreSQL остаётся источником истины.

### Принцип

Кешируются только `PlayerSettings`: максимум 512 записей, максимум 4 MiB сериализованных данных и TTL 30 секунд. Успешная запись обновляет локальную копию; ошибка записи инвалидирует её. Изменения с другого игрового сервера могут быть видны с задержкой не более TTL. Не кешируются состояние персонажа, инвентарь, баланс, транзакции, авторизация и межсерверное владение/перенос. Эти данные требуют PostgreSQL и проверок revision/идемпотентности.

После полной Steam-аутентификации настройки загружаются однопоточным bounded worker вне игрового потока; игровой поток применяет ответ только при совпадении SteamID и активного request ID игрока в том же слоте. Загрузка не задерживает появление в игре. Отсутствующая строка настроек трактуется как `{}` с revision 0 и кешируется на короткий TTL.

Этот кеш только локальный для процесса и не передаёт данные между серверами. Redis/общий LRU/прогрев остаются экспериментальными компонентами, исключёнными из стандартной сборки и не подключёнными к игровому lifecycle. Они не обеспечивают моментальный transfer.

## 26. Panorama UI Adapter

### Назначение

Работа с пользовательскими интерфейсами Panorama, если требуемые возможности доступны через поддерживаемые механизмы CS2. Particle UI применяется для специализированных меню и интерфейсов, которые практичнее или возможно реализовать только частицами.

### Предполагаемые применения

- карта мира;
- инвентарь;
- телефон;
- интерфейс заданий;
- меню персонажа;
- уведомления.

### Основные операции

- OpenPanoramaView
- ClosePanoramaView
- UpdatePanoramaData
- HandlePanoramaAction

### Ограничение

Серверный адаптер может адресно отправлять штатные текстовые сообщения CS2 через `TextMsg` в `HUD_PRINTNOTIFY`, `HUD_PRINTCONSOLE`, `HUD_PRINTTALK` и `HUD_PRINTCENTER`. Он сообщает поддержку текстовых уведомлений и доставки одному игроку; произвольные Panorama-панели, JS, обновление данных панели и клиентские действия возвращают `Unsupported`.

Нельзя считать гарантированными произвольное изменение клиентского Panorama, замену стандартного HUD или перехват всех клавиш только средствами серверного Metamod-плагина. ## 28. Input Manager

### Назначение

Преобразование доступных игровых действий в логические команды системы.

### Основные операции

- RegisterAction
- BindAction
- UnbindAction
- HandleInput
- PushInputContext
- PopInputContext

### Контексты

```text
GAMEPLAY
DIALOG
INVENTORY
MAP
VEHICLE
MENU
```

### Пример

```text
Физический ввод
      │
      ▼
Input Adapter
      │
      ▼
Logical Action
      │
      ▼
UI / Gameplay Module
```

### Ограничение

Сервер не получает автоматически доступ ко всем физическим нажатиям клавиатуры и мыши клиента. `InputManager` реализует контексты, логические действия и обработку фронтов кнопок из переданного снимка; это не означает, что Metamod сам перехватывает клавиатуру.

Для явного fallback поставляется необязательный клиентский `client/cfg/ow_keyboard_bindings.cfg`: `E` сохраняет `+use` и дополнительно отправляет серверу фиксированное действие инвентаря, `TAB` сохраняет `+showscores` и отправляет действие карты. Это не отключает/не заменяет стандартное табло и требует установки конфигурации самим клиентом. Прямой перехват клавиш и совместимость командного forwarding необходимо проверить в живом CS2.

Пока серверный UI-адаптер умеет только адресные `TextMsg`, действие карты показывает имя текущей карты и сообщает об отсутствии графической панели. Реальная карта, Panorama-панель и ее обновление остаются неподдержанными до появления подтверждённого клиентского UI-механизма.

# ЧАСТЬ XXVI. ПОТОКИ И ПРОИЗВОДИТЕЛЬНОСТЬ

## 42. Threading Model

### Основное правило

Операции с сущностями движка выполняются только в разрешённом контексте движка.

Фоновые потоки используются для задач, допускающих параллельное выполнение.

Например:

```text
                GAME THREAD
                    │
                    │ Request
                    ▼
                TASK QUEUE
                    │
                    ▼
                WORKER THREAD
                    │
                    │ Database / IPC
                    ▼
                RESULT QUEUE
                    │
                    ▼
                GAME THREAD
                    │
                    ▼
             APPLY GAME RESULT
```

### Требования

- не блокировать игровой поток ожиданием SQL;
- не обращаться к уничтоженным сущностям;
- проверять актуальность сессии при возврате результата;
- ограничивать очереди задач;
- корректно отменять операции при остановке модуля.

# ЧАСТЬ XXXI. ЭТАПЫ РЕАЛИЗАЦИИ

## 47. Этап 1 — техническая основа

Результат:

- загружается OW Core;
- работает Module Manager;
- загружается тестовый модуль;
- работают сервисы и события;
- доступны журналы ошибок.

## 48. Этап 2 — игроки

Результат:

- создаются сессии;
- загружаются персонажи;
- сохраняется состояние;
- обрабатываются отключения.

## 49. Этап 3 — два сервера

Результат:

- работают два процесса CS2;
- работает Coordinator;
- игрок переходит между серверами;
- восстанавливаются позиция и состояние;
- переход переживает типовые сбои.

## 50. Этап 4 — взаимодействия и интерфейс

Результат:

- игрок взаимодействует с объектом;
- открывается меню;
- обрабатывается выбор;
- интерфейс закрывается;
- сервер проверяет действие.

## 51. Этап 5 — NPC и диалоги

Результат:

- создаётся NPC;
- игрок начинает диалог;
- воспроизводится доступная озвучка;
- отображаются варианты ответа;
- выбор изменяет состояние задания.

## 52. Этап 6 — игровой мир

Результат:

- работают сектора;
- реализованы переходные зоны;
- сохраняется состояние мира;
- появляются игровые объекты.

Результат:

- инвентарь;
- экономика;
- задания;
- правила здоровья;
- правила оружия;
- социальные функции.

## 54. Этап 8 — транспорт

Результат определяется подтверждёнными возможностями движка.

Результат:

- нагрузочные тесты;

# ЧАСТЬ XXXII. КРИТЕРИИ ГОТОВНОСТИ

## 56. Минимальный рабочий прототип

Прототип считается успешным, если:

1. Два сервера CS2 работают одновременно.
2. Оба используют OW Core.
3. Игрок может подключиться к первому серверу.
4. Игрок получает игровую сессию.
5. Игрок взаимодействует с NPC.
6. Открывается пользовательское меню.
7. Игрок выбирает вариант ответа.
8. Сервер обрабатывает выбор.
9. Состояние персонажа сохраняется.
10. Игрок переходит на второй сервер.
11. Его состояние восстанавливается.
12. Повторный переход не дублирует данные.
13. При отключении игрока данные не повреждаются.
14. Необязательный модуль можно отключить через конфигурацию.
15. Ошибки отражаются в диагностике.

# ЧАСТЬ XXXIII. ЗАФИКСИРОВАННЫЕ РЕШЕНИЯ

## 57. Принятые решения

**ADR-001**

Использовать единое OW Core.

**ADR-002**

Основной серверный язык — C++.

**ADR-003**

Основная интеграция с CS2 — Metamod:Source и hl2sdk-cs2.

**ADR-004**

Игровые функции разделяются на модули.

**ADR-005**

Модули взаимодействуют через версионированные интерфейсы.

**ADR-006**

UI отделён от игровой логики.

**ADR-007**

Поддерживается несколько игровых серверов.

**ADR-008**

Состояние персонажей хранится независимо от конкретного процесса CS2.

**ADR-009**

Предпочтительная основная БД — PostgreSQL.

**ADR-010**

Критичные игровые действия проверяются сервером.

**ADR-011**

Первая версия модульной системы не обязана поддерживать горячую выгрузку DLL.

**ADR-012**

Бесшовность переходов, замена HUD и полноценный транспорт остаются исследовательскими задачами до технического подтверждения.

**ADR-013**

Единственное название проекта — CS2 Open World.

**ADR-014**

Particle UI является обязательной подсистемой интерфейса.

**ADR-015**

Основная логика проекта реализуется на C++.

**ADR-016**

Workshop используется для распространения ресурсов.

**ADR-017**

Карты и общие ресурсы распространяются отдельными пакетами.

**ADR-018**

Steam-аутентификация обязательна до предоставления игроку игровой сессии.

**ADR-019**

Ненулевой SteamID не является достаточным подтверждением авторизации; необходимо проверять состояние Steam-аутентификации клиента.

**ADR-020**

Transfer Manager разрабатывается как собственный компонент OW Core.

**ADR-021**

Встроенная мини-СУБД не разрабатывается; долговременное хранилище строится на PostgreSQL.

**ADR-022**

Разработка должна поддерживать запуск одного локального игрового сервера без обязательного отдельного кластера.

**ADR-023**

Реализация межсерверного транспорта исследуется на основе существующих решений и протоколов до выбора реализации.

**ADR-024 — открыто**

Конкретная библиотека Particle UI выбирается после рабочего прототипа на Metamod:Source и hl2sdk-cs2.

**ADR-025 — открыто**

Автоматический переход между серверами требует проверки в игре; команда клиенту `connect` является только кандидатом на прототип, а не гарантированной возможностью.

**ADR-026 — открыто**

Полная замена стандартного HUD требует отдельной проверки. Простые HUD-элементы следует реализовывать в Panorama, если это возможно штатными средствами.

# ЧАСТЬ XXXIV. НЕПРИНЯТЫЕ РЕШЕНИЯ

## 58. Открытые вопросы

Следующие решения пока не утверждены:

1. Точный механизм загрузки дополнительных DLL.
2. Конкретный ABI модулей.
3. Формат межпроцессных сообщений.
4. Конкретный транспорт сообщений.
5. Точная реализация пользовательского HUD в пределах поддерживаемых механизмов Panorama.
6. Конкретная библиотека Particle UI и её C++-адаптер.
7. Механизм обработки мыши.
8. Подтверждённый механизм перенаправления между серверами.
9. Формат пользовательских карт.
10. Реализация транспорта.
11. Реализация навигации NPC.
12. Возможность скрытия стандартного табло.
13. Возможность полноценной замены HUD.
14. Способ доставки пользовательских UI-ресурсов.
15. Максимальное число игровых серверов на одной машине.

Каждый вопрос должен быть закрыт отдельным техническим решением после проверки.

# ЗАКЛЮЧЕНИЕ

CS2 Open World строится как модульная многосерверная система.

OW Core предоставляет общую инфраструктуру.

Gameplay-модули реализуют игровую логику.

UI-адаптеры отвечают за отображение интерфейсов.

Coordinator управляет игровыми серверами и владением сессиями.

Persistence отвечает за долговременное состояние.

World Manager объединяет отдельные карты в единый логический мир.

Transfer Manager организует переходы между серверами.

Все подсистемы должны взаимодействовать через явно определённые интерфейсы и сообщения.

Главная цель архитектуры — обеспечить возможность расширять игровой мир, заменять отдельные реализации и развивать проект без необходимости переписывать всю систему.
